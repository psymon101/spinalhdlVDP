# Task 41 — Compositor Metadata Pipe

**Status:** Artifact phase
**depends_on:** [13]
**scope_boundary:** Metadata pipe definition and wiring only. No new compositor math, no new fetch formats.
**delivers:**

- Per-pixel metadata flag definition (math-enable, forced-priority, layer-source)
- Metadata carried through line-buffer boundary
- Compositor consumes metadata flags for color-math and priority decisions
- Explicit contract between fetch engines and post-compositor stages

**validation:**

- Sim: metadata flags generated by fetch engine arrive at compositor intact
- Hardware: visible proof that metadata-driven effects (e.g. forced-priority sprite) behave correctly

---

## 1. Goal

Define and wire a per-pixel metadata pipe that carries flag bits from the fetch engines (tile fetch, attribute decode, sprite eval) through the line-buffer boundary into the compositor, so that color-math and priority decisions can be driven by pixel metadata rather than global register state alone.

Today the compositor makes color-math and layer-priority decisions from global registers (`colorMath`, `layerEnable`). Task 41 adds per-pixel metadata so that individual pixels can override or augment those decisions — for example, a sprite pixel forcing priority above a background layer, or a tile pixel opting into color math.

## 2. Scope

### 2.1 In scope

1. **Metadata flag definition** — a compact, fixed-width bundle of flags per pixel:
   - `mathEnable` — this pixel participates in color-math blend (e.g. HDMA tint bands)
   - `forcedPriority` — this pixel wins priority regardless of normal layer order
   - `layerSource[1:0]` — which fetch engine produced this pixel (BG0, BG1, SPRITE, etc.)
2. **Line-buffer metadata carriage** — extend the existing line-buffer data path to carry the metadata bundle alongside RGB pixel data
3. **Compositor metadata consumption** — wire the metadata into the compositor priority and color-math stages so flags influence the output mux
4. **Fetch-to-compositor contract** — document the exact bit positions, valid/ready semantics, and default values when metadata is not yet generated by a given fetch engine

### 2.2 Out of scope (deferred)

- New compositor math modes (half/intensity, sub/add blend variants) — those are color-math engine tasks
- New fetch formats (2/4/8 bpp, packed attributes) — those are fetch-engine tasks
- Sprite evaluator metadata generation — the sprite evaluator will produce `forcedPriority` later; Task 41 defines the wire only
- Linestate / per-line scroll table — deferred to scroll-engine tasks

## 3. Architecture

### 3.1 Current state

```
Fetch engine(s) → [RGB+valid] → Line Buffer → Compositor → [final RGB]
                                      ↑
                                      └─ global regs: layerEnable, colorMath
```

The compositor decides:
- Which layer wins priority based on `layerEnable` and fixed layer order
- Whether color math applies based on global `colorMath` register

### 3.2 Target state (Task 41)

```
Fetch engine(s) → [RGB + metadata bundle + valid] → Line Buffer → Compositor → [final RGB]
                                                              ↑
                                                              └─ metadata flags per pixel
```

The compositor now decides:
- Priority: normal layer order, but `forcedPriority` overrides for this pixel
- Color math: global `colorMath` AND per-pixel `mathEnable` both required
- Layer source tracking for post-compositor effects (e.g. sprite-to-background collision)

### 3.3 Metadata bundle format

Proposed 4-bit bundle (width TBD by audit):

| Bit(s) | Name           | Description                                      |
|--------|----------------|--------------------------------------------------|
| 0      | `mathEnable`   | Pixel participates in color-math blend           |
| 1      | `forcedPrio`   | Pixel wins against all non-forced layers         |
| 3:2    | `layerSrc[1:0]`| 00=BG0, 01=BG1, 10=SPRITE, 11=reserved           |

Default value: `4'b0000` (no math, normal priority, source = BG0).

The bundle travels with every pixel through the line buffer and is consumed by the compositor at the same cycle as the RGB data.

## 4. Implementation Plan

### 4.1 HDL changes

1. **Define `PixelMetadata` bundle** in a new or existing SpinalHDL package:
   ```scala
   case class PixelMetadata() extends Bundle {
     val mathEnable    = Bool()
     val forcedPriority= Bool()
     val layerSource   = UInt(2 bits)
   }
   ```

2. **Extend line-buffer data path** wherever pixel data is buffered:
   - Widen the line-buffer RAM write/read data width by 4 bits
   - Or carry metadata in a shadow buffer if RAM port width is constrained

3. **Compositor wiring**:
   - Priority stage: if `forcedPriority` is set for a given pixel, that pixel wins regardless of normal layer order
   - Color-math stage: `globalColorMath && pixel.mathEnable` must both be true for blend to apply
   - Layer-source tracking: output the selected `layerSource` alongside final RGB for future collision/debug use

4. **Fetch-engine stubs**:
   - Tile fetch: drive `layerSource` based on which BG layer produced the pixel; tie `mathEnable` and `forcedPriority` to `False` for now
   - Sprite eval (future): will drive `forcedPriority` for sprite-zero-hit or similar effects; stub with `False` in Task 41

### 4.2 Register / bus impact

No new register-bus addresses. Metadata is entirely internal pipeline state.

### 4.3 Scenario impact

- Scenarios 0–17 should be **bit-for-bit identical** after Task 41, because all metadata defaults are zero (no math, normal priority, BG0 source)
- Sc33 (HDMA) already uses global `colorMath`; Task 41 does not change the visible output unless a fetch engine starts driving `mathEnable`

### 4.4 Validation plan

**Checkpoint A — Simulation:**
- SpinalHDL sim test that injects a pixel with `forcedPriority=1` and verifies the compositor selects it over a higher-layer pixel
- Sim test that injects `mathEnable=1` on a BG pixel and verifies color math applies only when global `colorMath` is also enabled

**Checkpoint B — Hardware:**
- Build a test scenario (e.g. Sc41) that drives `mathEnable` from a fetch engine and produces a visible HDMA-style tint band on a subset of pixels
- Capture and verify the band appears only where metadata asserts it

## 6. Risks & Mitigations

| Risk | Mitigation |
|------|------------|
| Line-buffer BRAM width already at port limit | Use shadow buffer or pack metadata into unused RGB bits |
| Combinatorial path through compositor gets too long | Register metadata one stage earlier if timing fails |
| Existing scenarios accidentally shift due to default-value bug | Sim regression against Sc0 before any hardware build |

## 7. Dependencies

- Task 13 (Multi-Layer Composition) — DONE. The compositor exists and can be extended.
- Task 33 (Copper-lite / HDMA) — DONE. Color-math path exists; Task 41 wires metadata into it.

## 8. Open Questions

1. **Bundle width**: Is 4 bits sufficient, or should we reserve more for future expansion (e.g. shadow/highlight, mosaic)?
2. **Shadow buffer vs. width expansion**: Does the current line-buffer BRAM have spare width for 4 more bits per pixel?
3. **Sprite evaluator integration**: Should Task 41 stub the sprite metadata input, or wait until the sprite evaluator is the active lane?
